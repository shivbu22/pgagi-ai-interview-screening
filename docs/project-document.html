Screenwise

AI Interview Screening System — Project Document
Take-home assignment for the PGAGI AI/ML Intern application  ·  Candidate: Shivam Yadav  ·  Stack: FastAPI + React (Vite) + SQLite  ·  Runs fully locally — no external API keys

1. Problem

Technical screening is expensive to do well. A recruiter or hiring manager must read each resume, work out what the candidate actually knows, and then prepare interview questions that are (a) relevant to the role, (b) grounded in the candidate's claimed experience, and (c) deep enough to separate real understanding from keyword familiarity. Done manually this takes 30–60 minutes per candidate and varies wildly between interviewers.

The assignment: build a system where a candidate uploads a resume, picks a target role, and the system dynamically generates interview questions from the resume plus a retrieval-augmented knowledge base whose primary source for AI/ML roles is Tom Mitchell's Machine Learning — with a frontend, a backend, and a database for sessions.

2. Solution overview

Screenwise implements the full pipeline in one local process:

  1. Parse. The resume (PDF via pypdf, or plain text) is parsed into a candidate profile: name, email, skills matched against a curated ~45-term lexicon, project titles extracted from the Projects section with layout-aware heuristics, and experience signals.
  2. Retrieve. A TF-IDF retriever ranks the 16 knowledge-base chunks against a query composed of the target role's focus terms and the candidate's own skills — so a candidate strong in neural networks is asked about neural networks, while a data-science candidate is steered toward Bayesian learning and evaluation.
  3. Generate. A deterministic composer assembles a 10-question set from three grounded sources (Section 4), each question labelled with its source and difficulty, and paired with a model-answer hint for the interviewer.
  4. Store. Sessions persist in SQLite and can be reopened from the UI's recent-sessions list.

3. Architecture

  React SPA (Vite build, served by FastAPI)

        ▼
  FastAPI backend
    ├── resume_parser.py   PDF/text → profile {name, email, skills,
    │                      projects, experience}  (pypdf + heuristics)
    ├── retriever.py       TF-IDF (scikit-learn) over knowledge_base.json
    ├── generator.py       deterministic 10-question composition
    ├── db.py              SQLite session storage
    └── data/knowledge_base.json   13 topics · 16 chunks · 32 questions

Stack choices. The brief permits React or Next.js on the frontend and FastAPI or Flask on the backend. This build uses a Vite-built React SPA served directly by FastAPI: an internal screening tool has no SEO or SSR requirement, and a single-process deployment keeps the demo runnable with one command. Modules are deliberately decoupled — only main.py knows about FastAPI; the parser, retriever, and generator are plain Python and unit-testable in isolation.

Why no LLM? The brief's hard constraint is that the system must run with no external API keys. Generation is therefore retrieval- and template-based (Section 4). This buys three properties an LLM call cannot guarantee: determinism (same resume + role → same interview), auditability (every question shows exactly which source produced it), and zero running cost. An optional LLM polish layer could be added behind an environment key without changing the pipeline, but the no-key path is complete by design.

4. RAG design and question generation

4.1 Knowledge-base construction

The KB follows the topic structure of Mitchell's Machine Learning (1997): concept learning, decision trees, neural networks, evaluating hypotheses, Bayesian learning, computational learning theory, instance-based learning, genetic algorithms, rule learning, analytical learning, and reinforcement learning. Every chunk is an original concept note written for this project — summaries, key points, and questions are paraphrases composed from the topic structure; no text from the book is reproduced. Each chunk contains: a 3–5 sentence summary, three key points, key terms, and two hand-written interview questions (with model-answer hints) tagged Basic / Intermediate / Advanced.

4.2 Retrieval

Each chunk is indexed as one TF-IDF document (title + summary + terms + key points, unigrams + bigrams, English stop-words removed). The query is the concatenation of (i) the role's focus terms — e.g. for AI/ML Engineer: neural networks, overfitting, decision trees, evaluation, generalisation — and (ii) the candidate's extracted skills and the role's focus skills. Cosine similarity ranks the chunks; the top 8 are returned with scores, which the UI displays so the interviewer can see why these topics were chosen for this candidate.

4.3 Composition

SourceCountHow it is produced
Knowledge base5Hand-written questions from the top-ranked chunks, one per chunk first, then a difficulty rebalance that guarantees at least one Advanced question in the set.
Resume-grounded3Templates instantiated with the candidate's actual extracted projects and skills ("In your project 'MARAT', what was the hardest technical problem, and how did you decide your approach worked?").
Role focus2If the role needs skills missing from the resume, honest gap questions ("This role works heavily with X… how would you get productive in two weeks?"); otherwise Advanced depth probes on matched focus skills, de-duplicated against the resume questions.

Every question carries a model-answer hint: for KB questions, the hint plus the chunk's key points define what a strong answer covers; for resume and role questions, the hint describes the evidence of depth the interviewer should listen for.

6. Verification

The system was tested end-to-end with a real resume PDF (the author's own AI/ML Engineer resume) through the running UI:

  • Parser extracted 22 skills and all 4 project titles (MARAT, AI Voice Receptionist, neteyes, PIKO (Nook)) — after two heuristic fixes for PDF line-wrap fragments.
  • Retrieval ranked Artificial Neural Networks (0.27), Reinforcement Learning (0.18), and Inductive Bias (0.12) highest for the AI/ML Engineer role given that resume's skills — a sensible match.
  • The generated set of 10 questions referenced the candidate's real projects and skills, spanned Basic → Advanced, and every hint expanded correctly in the UI. No console errors.

7. Limitations and next steps

  • Parsing heuristics. Section detection assumes conventional resume headings; heavily designed multi-column PDFs can parse imperfectly. A layout-aware parser (or an LLM extraction fallback behind an optional key) would harden this.
  • Lexical retrieval. TF-IDF matches words, not meaning. Swapping in a small local embedding model is the clearest quality upgrade and keeps the no-external-API property.
  • Question bank size. 32 hand-written KB questions plus templates keep generation deterministic but bound the variety; the bank is data, so it can grow without code changes.
  • Scoring. The system generates and explains questions but does not yet score candidate answers; rubric-based scoring against the KB key points is the natural next feature.
